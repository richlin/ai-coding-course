# Q-003 — How do you measure "time to accepted result" to optimize the dev loop?

The cost lesson defines "time to accepted result" as the right optimization target — the point when a change has passed required checks and a reviewer is willing to keep it.

**The open question:** What instrumentation or observation practice makes this measurable in practice? The components (model latency, tool execution, failed attempts, review cycles) are easy to list but hard to attribute. How do teams establish routing baselines from this metric rather than from per-request token cost?
