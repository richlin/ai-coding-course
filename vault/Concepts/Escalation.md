# Escalation

Returning a decision to a human when impact is high or evidence is insufficient, instead of letting the implementing agent resolve it unilaterally. Review checks correctness, regression risk, maintainability, security, and scope against the actual diff and behavior — not the agent's summary of what it did.

## Review ordered by risk

Authorization → data exposure → injection → state changes → maintainability. Trace untrusted data across input, transformation, storage, and output boundaries rather than reviewing only the files the agent's own summary mentions — a summary is generated by the same process being reviewed, so it inherits the same blind spots.

## Validation is not authorization

Confirming a value is well-formed (a valid email, a positive integer) says nothing about whether the caller was allowed to submit it in that context. Conflating the two is how authorization gaps survive review — the input "looks fine," so nobody asks who was allowed to send it.

## What a good escalation contains

Not a generic "is this okay?" — instead: the proposed behavior, the supporting evidence, the risk, and the specific decision needed. Separate fixable findings (resolve now, in this diff) from accepted-risk decisions (owned by a named, accountable person, with an explicit deadline) so that risk acceptance is visible rather than silently absorbed into the merge.

## The core rule

Do not let the implementing agent accept security or policy risk on its own authority, and do not grant broader permissions merely to avoid a focused approval step — see [[Permission Boundaries]] for the underlying consequence-tiered model this maps onto, and [[Approval Policy]] for the concrete matrix a team turns that model into.
